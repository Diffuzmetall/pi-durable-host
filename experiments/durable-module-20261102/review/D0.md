## Проверенные границы

- **Глубина модуля.** `session.ts:58–89` определяет конкретные операции и lifecycle owner, не произвольный dispatcher.
  Модуль скрывает native admission, observation, projection и cleanup; внешнему Host не нужны native handles.
  Это соответствует правилу arch: интерфейс скрывает изменчивые решения, а не просто переименовывает методы библиотеки.

- **Единственное исполнение.** Backend CONTRACT, раздел «Владение», оставляет один Harness на session object и прежний Store lock.
  Ни типы, ни примеры не вводят второй scheduler, registry выполнения или persistence owner.
  Реальное отсутствие второго owner ещё требует проверки D1; декларация не доказывает поведение.

- **Полномочия.** `session.ts:25–35` принимает доверенную server capability с действием и точным target.
  Backend CONTRACT:47–52 требует проверку внутри native commit и повторную проверку после await перед выдачей приватных данных.
  Parent operations остаются отдельными; `close` принадлежит lifecycle owner, не произвольному HTTP клиенту.
  Для `submission` runtime должен определить conversation по submission ID до проверки соответствующего target.

- **Публичные данные.** `api.ts:598–628` задаёт state и замену именованных секций, не raw delta paths или upstream WatchCall.
  `session.ts:51` допускает только новый observation union и существующий публичный doc frame.
  Backend CONTRACT требует allowlist документов, одинаковую очистку snapshot/update/history/receipt и безопасный отказ неизвестным ошибкам.
  Допустимый application/tool JSON не запрещается только из-за типа `unknown`; native handles через него передавать нельзя.

- **Доставка и история.** `api.ts:319–334` различает submission result, receipt и reconciliation.
  Backend CONTRACT:94–107 сохраняет requestId, fingerprint, atomic admission и retirement fence; отсутствие ACK не означает непринятие.
  History page отделена от context IDs; compaction/reset не разрешают удалить уже загруженные transcript pages.
  Ответ и `execution.busy` независимы. Producer overflow требует resync, не повторного send.

- **Владение файлами.** Backend CONTRACT содержит конкретные owning paths и запрещает blanket allowlist.
  SDK остаётся источником публичных DTO; native composition относится к runtime.
  Прямых native imports или `any`/unsafe casts в новых session/reducer types/examples не найдено.
  Полный транзитивный и compiled анализ относится к DM-B, не к этому утверждению.

## Обязательства интеграции, не новые блокирующие findings

**Eve: сохранить selection/connection fence перед reducer.** `observation.ts:22–27` принимает любой полный state того же scope.
После `agent.end/revoked` поздний state того же scope снова заполнит reducer; update после end потребует resync.
Это детерминированный вывод из исходника, не воспроизведённый runtime incident.

SDK CONTRACT:64 уже возлагает selection epoch/AbortSignal fence на UI; reducer не является самостоятельной границей авторизации.
D1 должен исключать frames старого подключения и автоматический reconnect после revoke.
Нужна проверка позднего same-scope frame после revoke/reconnect, а не только чужого conversation ID.

**Carol/Eve: не превратить uncertainty в повтор эффекта.** После достоверного `accepted:false` старый ключ уже retired.
Backend CONTRACT:104 требует conflict для запоздавшего send с этим ключом.
Фразу SDK CONTRACT:86 про повтор прежнего requestId необходимо применять без обхода этого fence.
Retry lookup и resync не являются разрешением заново исполнить retired submission.

**Carol: реализовать, затем проверить заявленную атомарность.** TypeScript interface не обеспечивает выполнение `assertCurrent` внутри commit.
D1 должен проверить revoke во время await/commit, чужой submission/parent target и запрет документов до observer.
Эти требования уже есть в producer contract; review не заменяет отрицательные runtime проверки.
