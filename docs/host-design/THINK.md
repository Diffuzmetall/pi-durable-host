# THINK: дорабатываем Disler, не строим новый framework

Решение от 2026-10-28. Входные данные: [OBSERVE](OBSERVE.md), ответы пользователя в conversation 1/982 и окончательный выбор Disler после исследования Pocket. Требования: [ISA](../../ISA.md).

## Выбранный путь

Сохранить `apps/dpi-backend` и `apps/dpi-sdk` как продуктовую основу. В backend изменить сборку runtime, admission/authority и необходимые projection-поля. Наш TUI подключить через SDK, сохранив его интерфейс. BB и iii получают свои пакеты позже.

Полезный первый результат — один настоящий разговор на 1.4.0, доступный через API и наш TUI, продолжающий работу после отключения TUI. Пустой набор новых пакетов или новый «универсальный runtime core» этим результатом не считается.

## Почему не остальные варианты

| Вариант | Что сохраняем | Что придётся делать | Решение |
|---|---|---|---|
| Fork Disler + узкие изменения | Backend, wire types, SDK, streams, fixtures, repo history | 1.4, наш profile, права, receipts, remote-controller TUI | Выбран пользователем |
| Обернуть только текущий terminal host HTTP-сервером | Наши integrations и controller | Заново создавать каталог, SDK, transport и клиентские projections | Больше дублирования готового Disler |
| Взять Pocket за основу | Готовое web-приложение на 1.4 | Согласовать Pocket-specific состояние и наши клиенты/authority | Исключён пользователем |
| Новый host framework с абстрактным engine API | Формальная свобода реализации | Повторить уже имеющиеся backend и SDK; поддерживать новый слой | Не соответствует reuse-first |

Это выбор границ, не доказанная оценка сроков. Более маленький репозиторий сам по себе не означает более короткую интеграцию.

## Минимальный набор новых решений

### 1. Одна точка сборки runtime

Сейчас `Store.openAgent` напрямую устанавливает CodingTools, playground, jobs и add-ons, затем создаёт Harness. Именно здесь подключается доверенная фабрика profile. Сначала это локальный модуль backend, а не отдельная система plugins, DI-container или универсальный engine interface.

Минимальный profile умеет создать runtime с faux или явно выбранным провайдером. Наш profile переносит существующие модели, инструменты и authority hooks. Не надо переносить весь каталог release, runtime installer и зависимости VPS. Не надо автоматически загружать все обычные Pi extensions.

Factory вызывается только после проверки выбранного владельцем profile и версии. HTTP caller не передаёт путь к модулю и не получает возможности менять registry.

### 2. Публичный контракт остаётся у dpi-sdk

Сохраняем `/v1`, идентификаторы session/agent, REST и SSE. Новые capabilities и receipts добавляются к существующим типам. Отдельный `host-contract`, второй SDK, gRPC, GraphQL и event broker пока не нужны.

BB/iii версии не становятся версиями host. Совместимость определяется protocol major и обязательными capabilities. Для текущего изменения достаточно старого и нового клиента в одном integration fixture; нельзя обещать бессрочную совместимость всех исторических версий.

### 3. Авторизация предшествует native admission

Существующий device bearer оставляет слишком широкие права. Сохраняем способ аутентификации, но добавляем серверную привязку credential к scope, session/conversation и категории отправителя. Observer не отправляет команды. Machine grant не разрешает human admission. Полномочия BB и iii привязаны к текущим binding/revision.

Проверка HTTP не заменяет native admission. Изменившаяся policy должна быть замечена у owning boundary, включая queued admission. Native parent-control не заменяется endpoint вида «остановить любой task по id».

### 4. Надёжность без обещания exactly-once для внешнего мира

Клиент сохраняет requestId до первого submit. Host связывает его с аутентифицированным actor, session, conversation, видом операции и fingerprint тела. Повтор читает receipt или сверяется с native submission; другой payload конфликтует.

Durable остаётся владельцем принятой работы. Не добавляем отдельную очередь выполнения рядом с ним. Catalog может хранить create intent/receipt, но не становится вторым scheduler. Если сбой не позволяет определить итог внешнего эффекта, состояние остаётся uncertain и unsafe tool не переигрывается автоматически.

### 5. Процессы выбираются по конкретному препятствию

Простой baseline Disler размещает несколько Harness в одном процессе. У нашего profile доказаны process-global настройки. Поэтому его нельзя сразу включить в этот режим.

В P0 сравниваются два ограниченных решения:

- Убрать конкретные глобальные настройки у owning integration: передать session-local paths/identity/dispatcher. Это предпочтительно, если не требует переписывания зависимостей.
- Изолировать полную session в дочернем процессе. Общий backend оставляет каталог и внешний API; native runtime и session SQLite принадлежат только worker.

Отдельный процесс — безопасный исходный вариант для неперенесённых globals, но не «бесплатная обёртка». `routes.ts` и `Store` сейчас работают с реальным Harness/Conversation. Нельзя подменить его прозрачным remote proxy и скрыть смену семантики. P0 должен показать необходимую грань session-операций и её цену; [ARCHITECTURE](ARCHITECTURE.md) обозначает условную process boundary явно.

Сразу поддерживать оба process modes в продукте не требуется. Выбираем одну доказанную схему. Новый worker framework, plugin bus, HTTP-порт на каждый tool и распределённый scheduler не нужны. Single-session pilot допустим, но не закрывает критерии изоляции двух sessions.

## Продуктовые сценарии вместо новых функций

1. Терминал отправил задачу, закрылся; второй клиент показывает тот же результат, а не новый запуск.
2. Соединение пропало после принятия команды; клиент восстанавливает receipt, не создаёт второй запрос.
3. Агент ждёт решения; пользователь видит конкретный запрос после reconnect. Клиент не принимает решение за него.
4. Обновился BB; обновляется BB adapter, а terminal package остаётся прежним.
5. Разработчик добавил свой native extension; простой клиент видит доступную capability и безопасный текст, не скачивает код расширения.

## Применённые инженерные правила

- `Laziness Protocol`: сохраняем существующие каталоги и SDK; не создаём новый core ради предполагаемой универсальности.
- `Experience First`: сохраняем наш TUI и приоритет terminal → BB → iii; не делаем playground обязательным этапом.
- `Clean Architecture`, lightest enforceable boundary: отделяем клиента от execution owner. Это не основание превращать каждый модуль в сервис.
- `Clean Architecture`, incremental extraction: меняем `openAgent` и admission в местах их владения; не копируем симптомы в каждом adapter.

## Проверки, способные изменить техническую часть решения

| Гипотеза | Опровержение | Следующее действие |
|---|---|---|
| 1.4 подключается к существующему backend без нового ядра | Требуемые операции не выразимы через поддерживаемый SDK | Зафиксировать точный API gap и минимальный patch; не заменять SDK |
| Process globals можно изолировать узким изменением | Две sessions всё ещё смешивают identity/logging или ломают close | Выбрать session process и проверить ownership/recovery |
| Native request receipt закрывает потерянный ACK | Crash fixture создаёт второй submission | Исправить admission boundary до расширения числа клиентов |
| Наш TUI отделим по controller/view | Код рендера требует owning Harness | Локально разделить UI и execution; не заменять UX на Disler TUI |

Выбор Disler уже закрыт пользователем. Эти проверки уточняют реализацию внутри выбранной основы, а не запускают очередной поиск другого продукта.
