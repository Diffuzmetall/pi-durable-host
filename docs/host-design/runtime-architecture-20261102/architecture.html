01 / Как устроено целое

Один переход по сети.
Один движок исполнения.

Terminal, iii и будущий BB работают через общий прикладной контракт. Ни один интерфейс не открывает второй Harness для той же сессии.

Runtime и владениеКлиентское приложениеОтложенная интеграция

Движок и ядро продукта

Движок — upstream Durable. Фоновое ядро продукта — Host с runtime-модулем и Durable. Между ними нет ещё одного daemon.

Глубокий модуль

Он скрывает native lifecycle, admission и формат состояния. Он не повторяет все методы Harness под другими именами.

02 / Что действительно показывает Herdr

Независимость появляется там, где разделено владение.

Herdr App организует окно. Core предоставляет терминалы и API. Ещё ниже holder сохраняет живые программы при обновлении core.

Берём принцип

Клиент не владеет работой

Версионируемый API, согласование возможностей, snapshot после reconnect, отдельные пользовательские модули и сохранение прежней рабочей версии.

Не копируем механизм

Holder не заменяет Durable

PTY-holder сохраняет процессы. Durable сохраняет агентное исполнение. Добавление holder не делает безопасной смену JS-кода, definitions или формата БД.

Модульность не является sandbox. Herdr mods могут запускать программы и обращаться в сеть. Native extensions тоже исполняют доверенный код. Узкий interface уменьшает связанность, но сам по себе не ограничивает права процесса.

Почему Pocket тоже полезен для сравнения

Pocket — приложение-Host поверх Durable. Его extension module получает host и web; routes и cleanup подготавливаются перед commit. Изменения server core требуют restart.

Прочитан локальный checkout Pocket 0.26.0 с Durable 1.4.0. В нём Hindsight напрямую подключён к PocketApp, поэтому «всё независимо» было бы преувеличением. Берём staged registration и lifecycle, а не меняем наш Host на Pocket.

04 / Поведение важнее названий пакетов

Потерянный ответ — не повод повторять действие.

Клиент хранит requestId. Host принимает команду атомарно с проверкой прав. При обрыве соединения клиент выясняет исход и заново получает состояние.

Наблюдение — не исполнение

При revision gap клиент запрашивает новый snapshot. Disconnect закрывает observer, но не является interrupt. Старая команда не отправляется повторно ради восстановления UI.

Ответ — не всегда idle

Фоновая task может продолжаться после ответа. Transcript сохраняет историю, даже когда compaction изменяет context модели.

Независимо не значит всегда горячо.

Горячая замена расширения

01 / PREPARE

Подготовить

Загрузить код и проверить совместимость без публикации новой регистрации.

02 / COMMIT

Переключить

Новые вызовы получают новую версию через прежний registry.

03 / DRAIN

Дождаться старых

Уже начатые вызовы сохраняют нужные им код и ресурсы.

04 / CLEANUP

Освободить

Закрыть старые listeners и connections после безопасного завершения.

Ошибка подготовки → discard кандидата. Прежняя рабочая версия остаётся доступна. Reload не расширяет права и не превращает неизвестный persisted format в совместимый.

Обновление движка

01 / BUILD

Отдельная сборка

Точные dependencies, bindings и происхождение patches.

02 / QUALIFY

Изолированная среда

Настоящие runtime, SQLite и transport. Нет доступа к production secrets.

03 / ACCEPT

Один digest

Source review и installed QA проверяют один immutable candidate.

04 / OPERATOR

Отдельное разрешение

Документ и зелёные тесты сами по себе не активируют release.

Не запускать Durable 1.4 на БД, изменённой 1.5. Возврат к исходной backup-copy и совместимый возврат с текущей историей — разные гарантии. Backup может потерять новые данные и не отменяет внешние эффекты.

Почему версия API не равна версии Durable

В текущем SDK объявлены API_VERSION = 2 и agent-state.v1. Это наш прикладной контракт, а не Durable 2. Версии runtime, клиента и extensions изменяются по собственным правилам совместимости.

Наша прикладная логика может остаться прежней, а native binding потребовать адаптации. У стороннего пакета, импортирующего Durable, своя совместимость. Безусловную поддержку любых будущих releases не обещаем.

06 / Как отличить архитектуру от красивой картинки

Доказываем на неизменном клиенте и настоящем runtime.

Первый результат — один работающий terminal roundtrip на 1.5. Затем тот же client artifact проверяется с настоящими 1.4 и 1.5 в отдельных средах и БД.

Что проверять

  • Send → tool → answer → reconnect.
  • Нет утечек Harness, Tx, LiveDoc и WatchCall.
  • Revoke перед native commit, lost ACK и resync.
  • Безопасные snapshots и updates.
  • Busy reload, cleanup и отказ несовместимой версии.
  • Recovery без повторного внешнего эффекта.

Что видно в исходниках

Контракт существует

DurableSession и protocol 2 уже описаны. Но на прочитанном срезе routes.ts ещё использует Harness, а streams.ts — watchEvents.

Это переходная реализация, не доказательство завершённой границы. Runtime-тесты в этой работе не запускались.

Как применена взаимозаменяемость агентов

Задача должна передаваться другому разрешённому исполнителю через контракт, checkpoint и evidence. Но два агента не становятся одновременно владельцами одной сессии или одного claim.

Существующий DeLM и его ownership сохраняются. Новая команда, board или loop не создаются. Независимый проверяющий не принимает собственную реализацию.

Следующий шаг уже есть в DM1. Подключить семантический session owner к реальному Host и проверить D1. Не переписывать transport и не внедрять Herdr ради сходства со схемой.
