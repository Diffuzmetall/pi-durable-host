## 4. Повторно подтверждённые дефекты запуска

### Обработка остановки устанавливалась слишком поздно

В исходном `operational-service.mjs` SIGINT/SIGTERM обрабатываются только после завершения `Store.open()`. Воспроизведён сценарий: Store уже создал настоящий временный lock, затем получил сигнал до окончания открытия. Исходный процесс завершался сигналом, не освобождая lock.

В кандидате обработчик установлен во время ожидания `Store.open()`. Остановка дожидается завершения открытия, закрывает Store и не объявляет HTTP readiness. Повторные сигналы используют один cleanup promise.

Это исправление штатной остановки, а не мгновенная отмена зависшего initializer. От SIGKILL оно не защищает, автоматическое удаление блокировок не добавлено.

### Бюджеты ожидания не согласованы

- Рабочий сервис допускает запуск до 300 секунд.
- Исходный terminal launcher ждёт только 45 секунд.
- Рабочий сервис даёт остановке только 60 секунд, что недостаточно для ожидания долгого открытия.
- В отдельном старом `activate-delm.mjs` subprocess timeout равен 80 секундам. Этот helper также рассчитан на `DELM-RELEASE.json` и автоматически отправляет модельное continuation-сообщение; его нельзя слепо использовать для нового unified-release.

Кандидат launcher ждёт 330 секунд. Подготовлен, но не установлен drop-in с `TimeoutStartSec=300` и `TimeoutStopSec=300`. Будущая процедура переключения также должна ждать готовности не меньше service budget и не отправлять побочные модельные сообщения без разрешения.

## 6. Почему рабочее переключение пока не выполнено

Действующий `AGENTS.md` прямо запрещает P6/production activation и изменение установленных runtime releases. Также общие source writes требуют узкой board lease; инструменты `context` и `delm_wait` исходной команды в этом операторском сеансе не доступны. Чужая actor identity не использовалась для обхода этого ограничения.

Поэтому исправления сохранены отдельным кандидатом; source patch не применён. Рабочий Host, unit, auth, MCP, bindings, история и сохранённые модели не изменялись. Штатный read-only `verify` не создавал новую команду и не отправлял prompts.

Для продолжения нужен разрешённый проектом путь интеграции и одной production-активации. Живой прогон моделей, особенно двух ранее упавших моделей `opencode`, требует отдельного разрешённого объёма; локальные faux-тесты не подменяют такой результат.

## 7. Порядок следующего шага

1. Согласовать разрешения проекта и владельца общей записи. Применить проверенный patch, затем собрать новый кандидат со всеми ранее подготовленными изменениями. Установленные releases не переписывать на месте.
2. Проверить именно конечный артефакт, зависимости и rollback. Самостоятельные исходные проверки не считать приёмкой установленного release.
3. Перед переключением снять свежий снимок сессий, моделей, истории, задач и расписаний; дождаться безопасной остановки и сохранить резервную копию. Не удалять существующие locks автоматически.
4. Выполнить одну разрешённую активацию с согласованными start/stop/launcher budgets. После готовности подтвердить фактический release, HTTP, capabilities и сохранность исходного состояния.
5. Восстановить Rex-представление той же восьмёрки без создания новых Host-сессий. Только после read-only проверки доставить разрешённые сохранённые задания с исходными request IDs.
6. Оценивать DeLM отдельно по доставке, ответам каждого участника, работе с доской, durable wait/wake и read/ACK. Ошибки модели не скрывать заменой модели или сокращением числа участников.

**Итог:** локальный механизм DeLM проходит проверенные faux-сценарии, но последний живой smoke был успешен не у всех моделей, а восьмёрка осталась подготовленной, не запущенной. Исправленный startup-кандидат проверен; рабочее обновление ещё не выполнено.
