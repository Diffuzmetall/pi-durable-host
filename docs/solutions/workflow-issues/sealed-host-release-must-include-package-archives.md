# Исправление Host должно пережить повторную сборку из архивов

## Context

При восстановлении SSE обнаружилось расхождение между ранее проверенным исправлением и следующим активным Host: большой snapshot приходил, но четыре следующих документа отсутствовали. Проверка того, что Host запущен и отдаёт HTTP 200, этого не обнаруживала. Возврат целого старого кандидата ради SSE или версии MCP потерял бы более поздние изменения каталога моделей, reload и запуска.

В этом разборе есть один решённый workflow-дефект: **проверенное изменение в установленном дереве не является устойчивой поставкой, пока следующий путь сборки из package archive может вернуть старый код**. Причина сетевой недоступности отдельных MCP-серверов сюда не включается: она остаётся незакрытой.

## Guidance

Собирать изменение поверх действующего согласованного release, а не поверх удобного, но устаревшего кандидата. Сверять три представления одного результата:

1. Owning source: исправление в `apps/dpi-backend/src/streams.ts:251` и pin зависимости в manifest/lockfile.
2. Installed package: тот JavaScript и та версия зависимости, которые действительно будет загружать operational service.
3. Package archive: архив, из которого будет сделана следующая установка, и его integrity-записи.

Операции этого конкретного восстановления находятся в `experiments/host-sse-mcp140-20261031/finalize.py` и `experiments/host-sse-mcp140-20261031/seal.py`. После обновления установленного backend был пересобран его архив и согласованы lock integrity records. Финальная проверка запускалась **на запечатанном release**, а не только на промежуточной копии.

Для SSE разделять начальную передачу и обычный backlog. В owning source граница буфера задаётся в `apps/dpi-backend/src/streams.ts:13`; ожидание `drain` или `close` перед документами находится в строках 251–265. Исправление initial snapshot не должно превращаться в снятие ограничения для действительно медленного зрителя.

## Why This Matters

Source-only PASS не отвечает, какой пакет запустит service. Installed-only PASS не отвечает, сохранится ли исправление после установки из архива. Проверка manifest доказывает целостность выбранных файлов, но сама по себе не доказывает правильность поведения. Нужен поведенческий тест, привязанный к этому же набору файлов.

В рассматриваемой работе исходный large-snapshot regression сначала воспроизвёл потерю всех четырёх документов. SSE-only исправление прошло 2/2 проверки; объединённый окончательный release — 17/17 без пропусков в изоляции. После разрешённого включения реальный snapshot размером 3 089 294 байта получил все четыре документа на том же соединении, с одним snapshot и без модельного запроса. Это разные доказательства, а не взаимозаменяемые счётчики тестов.

## When to Apply

- Изменяются installed-пакеты, а следующие candidates собираются из сохранённых tarballs.
- Одновременно сохраняются ранее принятые интеграции и обновляется одна зависимость.
- Несколько команд независимо называют свои артефакты «проверенным кандидатом».
- Нужен rollback, который не подменяет release более старым набором возможностей.

## Examples

Недостаточно: исправить `streams.ts`, получить зелёную компиляцию и переключить service на другой каталог с похожим названием.

Достаточное доказательство этого кейса: source regression → пакет и архив с тем же исправлением → exact sealed-release regression → разрешённый cutover с проверкой сохранности → read-only проверка рабочего SSE. Приватные backup, receipts и история остаются вне Git; публичный отчёт содержит критерии, результаты и fingerprint release.

Не скрывать отрицательные результаты соседних проверок. В `experiments/host-activation-20261031-terra8/retained.test.mjs` отдельно проверяется, что потеря внешних MCP-инструментов даёт `mcpParity: false`, даже при сохранении данных/native. Это **не полный PASS системы** и не доказательство исправления MCP.
