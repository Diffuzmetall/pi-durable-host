# Zero как неизменённая библиотечная основа

Документ объясняет рекомендуемую целевую архитектуру. Эта архитектура ещё не реализована.

Основание приведено в [исследовании OBSERVE](OBSERVE.md). Выбор и ограничения библиотечной композиции описаны в [сравнении THINK](THINK.md).

## 1. Решение в одном абзаце

Предложение сохраняет наш Host, SDK и терминал. Интеграция с native API выделяется в `@dpi/runtime-zero`, а код отдельных возможностей размещается в пакетах. Интеграция использует публичные компоненты Zero и Pi Durable, который прошёл проверку совместимости. Исходники Zero не меняются.

Наш пакет собирает полный профиль, устанавливает политики и связывает сервисы до `resume`. Клиенты не зависят от способа сборки среды исполнения.

Имена `@dpi/*` обозначают предлагаемые пакеты. Эти npm-пакеты не опубликованы. Обозначения не подтверждают владение пространством имён npm.

## 2. Компоненты и направление зависимостей

```text
 dpi-terminal-adapter     dpi-bb-adapter      dpi-iii-adapter
         │                     │                   │
         └─────────────────────┼───────────────────┘
                               ▼
                            dpi-sdk
                   публичные DTO / HTTP / SSE
                               │
                               ▼
                         dpi-backend
             authentication · grants · session catalog
                               │
                    semantic session contract
                               ▼
                       @dpi/runtime-zero
           admission · projection · lifecycle · reload
                  │                         │
       @dpi/profile-personal                │
         │                                  │
         ├─ @dpi/extension-tools             │
         ├─ @dpi/extension-mcp               │
         ├─ @dpi/extension-memory            │
         ├─ @dpi/extension-automation        │
         └─ существующий DeLM package        │
                  │                         │
                  └──────────┬──────────────┘
                             ▼
              публичные компоненты durable-zero
                   + native Pi Durable SDK
                             │
                    один Harness на session
                             │
                   SQLite · native scheduler
```

Диаграмма показывает зависимости и состав системы. Она не требует отдельного слоя вызова для каждого сообщения. Сервер выбирает профиль. Пакеты отдельных возможностей не импортируют backend, SDK или терминал.

Код привязки к native API может зависеть от Pi Durable. Прикладные алгоритмы пакетов не должны зависеть от типов Zero, HTTP, идентификаторов BB threads или элементов интерфейса терминала. Дополнительные пакеты `*-domain` без второго потребителя не нужны. Достаточно внутренних файлов и публичных exports пакета.

## 3. Что используем из Zero

| Exported capability | Использование | Граница |
|---|---|---|
| `BuiltinExtensionRegistry` и `BuiltinExtension` | Подключение package definitions и упорядоченный teardown | Не считать полным session lifecycle |
| `adaptExtensionTool`, `installExtensionTools` | Адаптация выбранных обычных Pi tools | Проверить guards, schemas, cancellation и structured output |
| `createNestedToolExecutor` | Возможный reuse nested dispatch | Не выпускать, пока direct/nested не проходят одинаковые policy checks |
| `createPiPrompt`, dynamic sections/namespaces | Подходящие части prompt/discovery composition | Не перезаписывать наши context/memory policies |
| `mountExtensionBridge` | Для пакетов с подходящим поведением при запуске и формировании контекста | Создаёт собственный runner и рано отправляет `session_start`. Не обеспечивает полную адаптацию любого расширения |
| `ViewStreamProjector` и projection helpers | Внутренняя обработка подходящих представлений | Публичный wire остаётся нашим; privacy проверяется отдельно |
| `openDurable({builtins})` | Минимальная feasibility-ветвь B | Не использовать вместе с собственным Harness; полный профиль пока блокирован |
| `DurableEngine` | Узкий пользовательский facade Zero | Не расширять его возможности заявлениями о чужих options |

Штатные subagent, CodeMode и MCP не должны дублировать наших владельцев этих возможностей. Компонент подходит для повторного использования, только если его поведение соответствует нужному контракту. Наличие export не требует импортировать весь набор.

Наш код запуска не должен копировать `runtime-loader.ts`. Композиция использует текущий профиль Host, его lifecycle и native API. Если интеграция требует копирования внутренних модулей Zero, работу необходимо остановить. Такая копия была бы fork, а не независимым пакетом.

## 4. Единственный владелец и процессы

Логически один Host обслуживает несколько клиентов и сессий. Одна session имеет один Harness, один native scheduler и один владеющий Storage lifecycle.

Для начальной проверки допустима одна сессия в одном Host-процессе. Для полного профиля с несколькими сессиями предложен отдельный worker на активную сессию. Эта рекомендация действует до подтверждения безопасной совместной работы компонентов с общим состоянием процесса.

```text
Host service
  ├─ HTTP/SSE + auth + catalog
  ├─ session A worker → runtime-zero → один Harness → A.sqlite
  └─ session B worker → runtime-zero → один Harness → B.sqlite

Terminal / BB / iii → Host service, а не напрямую в SQLite/worker
```

Причина разделения сессий связана с общим состоянием штатного CodeMode Zero, среды исполнения и конфигурации. Это не предложение создать микросервисы. Worker не является новым агентом, внешним daemon или вторым scheduler. Native tasks по-прежнему планирует Pi Durable.

Внутренний канал обслуживает текущие операции сессии, а не произвольную RPC-шину. При реализации необходимо подтвердить, что Host уже предоставляет подходящие процессы и межпроцессный обмен. Этот исследовательский пакет их не создаёт.

Закрытие терминала снимает подписку, но не закрывает worker сессии. Перезапуск worker является отдельной операцией lifecycle. Блокировка должна запрещать двум владельцам открыть одну сессию. Путь сокета или наличие файла не доказывают исключительное владение.

## 5. Запуск полного профиля

Ниже описан целевой порядок внешней композиции C. Это не существующий callback API Zero.

1. Host определяет identity сессии, рабочий каталог и профиль по доверенной конфигурации. Клиент не задаёт путь импорта или credentials среды исполнения.
2. Интеграция проверяет набор пакетов, совместимость зависимостей и definitions, а также единственного владельца. Неизвестное состояние приводит к отказу до `resume`.
3. Профиль создаёт отдельные экземпляры пакетов для каждой сессии. Политики, конфигурация и каталоги передаются явно.
4. Их definitions устанавливаются в один native registry. Каждый транспорт subagent, CodeMode и MCP получает одного владельца.
5. Интеграция открывает один Storage и Harness с защищённой средой исполнения и необходимой native-проверкой полномочий перед commit.
6. Memory, automation, tracing и другие сервисы с состоянием связываются с этим Harness и исходным Storage.
7. Интеграция подключает наблюдение и безопасную проекцию. Она назначает владельцев обработки ошибок и очистки ресурсов.
8. После всех обязательных привязок выполняется native `resume`. Сессия переходит в состояние `ready`.

При ошибке до `ready` профиль не должен работать частично. Очистка закрывает созданные ресурсы в обратном порядке. Ошибка очистки не скрывает исходную ошибку. Клиент получает структурированную ошибку без путей, credentials и stack trace.

В варианте B пункты 5–8 выполняет Zero. Внешняя привязка до `resume` отсутствует. Поэтому вариант B не реализует описанный порядок.

## 6. Внутренний контракт Host с интеграцией среды исполнения

Контракт основан на существующем `apps/dpi-backend/src/durable/session.ts`, а не на новом универсальном `execute(method,args)`. Он включает следующие операции.

- Отправку, receipt, reconcile и результат допуска отправки.
- Прерывание через `interrupt`.
- Чтение истории и контекста, наблюдение.
- Настройку через `configure` и обновление через `reload`.
- Состояние, команды, receipt и reconcile родительского управления.
- Закрытие владельца.

Интеграция получает identity и доступ в пределах разрешений, а не HTTP request или исходный bearer token. Native Harness, Storage, Registry, Tx, WatchCall и приватные документы остаются внутри пакетов интеграции.

Устойчивый `requestId` связан с actor, payload, сессией и разговором. При потере подтверждения Host использует receipt и reconcile. Отказ клиента не разрешает автоматическое повторение действия. Результат обработки команды отличается от результата работы агента.

`prompt(): Promise<void>` Zero не является достаточным доказательством admission. Некоторые операции нельзя безопасно выразить через публичный native API и согласованный authorization hook. Такие операции остаются недоступными. Для них нельзя ослаблять проверку прав.

## 7. Как работают будущие BB и iii

### Общая часть

Оба адаптера используют `dpi-sdk`, прежние идентификаторы сессии и разговора, публичное состояние, историю и receipts. Они не устанавливают расширения среды исполнения, не выбирают native models напрямую и не открывают базу сессии.

Начальное согласование возможностей описывает доступные операции и функции интерфейса. Номер Host API не зависит от версии Zero. Host отклоняет неподдерживаемую мутацию до внешних эффектов. Описание возможностей не выдаёт полномочия.

### BB

Адаптер BB сопоставляет thread и turn существующим серверным привязкам сессии и разговора. Повторный turn сохраняет идентификатор запроса. Сервер проверяет управление дочерними и родительскими агентами. Проекции BB не определяют результат native-исполнения.

Отключение BB означает detach, а не abort. BB отображает функции интерфейса доступными ему средствами. Отсутствие renderer не разрешает запуск произвольной функции серверного расширения в браузере.

### iii

Адаптер iii получает delegated identity, инструменты в пределах разрешений и политику admission. Он не получает полномочия человека, владельца всех сессий или право подтверждать Goal от имени человека. Результат связан с устойчивыми идентификаторами отправки и ответа.

Клиент без интерфейса не отвечает автоматически «да» на запрос подтверждения. Обязательное решение человека требует разрешённого интерактивного канала. Без такого канала операция сообщает об ожидании или недоступности и не выполняет защищённое действие.

### Порядок

Сначала требуется сквозная проверка терминала. BB и iii проверяются как отдельные потребители того же API, а не новые ветви среды исполнения. Их реализация начинается после готовности общего поведения первого среза.

## 8. Интерфейс наших расширений без изменений Zero

Предложение разделяет три части расширения.

1. Серверная логика включает tools, hooks и native-состояние.
2. Сериализуемые запросы интерфейса включают выбор, ввод, уведомление и статус.
3. Клиентское отображение использует элементы терминала или средства BB.

Для адаптируемых пакетов профиль может передать функции `notify`, `requestInput`, `requestConfirmation`. Это обычные параметры зависимостей конкретных пакетов, а не обязательный новый SDK для всех расширений. Host направляет запросы авторизованному клиенту.

Каждый запрос содержит идентификаторы сессии, разговора и самого запроса, а также допустимый тип ответа. Host не принимает ответ от другого клиента или после отмены. Повторные ответы не повторяют действие. Переподключение восстанавливает ожидающий запрос интерфейса, а не запускает инструмент заново.

`ctx.ui.custom(renderFunction)` не пересылается. Если нужен собственный renderer, для него выделяется локальная точка входа терминала. Серверная бизнес-логика повторно не загружается. Другие клиенты получают доступную проекцию либо явный отказ. Скрытое исполнение серверного кода в клиенте не допускается.

Прозрачная поддержка произвольных сторонних Pi UI extensions на штатном Zero не заявляется. Если Zero bridge не обеспечивает привязку до запуска, внешняя композиция может использовать штатный Pi ExtensionRunner напрямую. Совместимость этого варианта требует отдельной работы. Поддержка без адаптации не обещается.

## 9. Reload и обновления

Обновление включает три независимые операции.

| Изменение | Владелец | Смысл |
|---|---|---|
| Renderer терминала, BB или iii | Клиентский пакет | Переподключение без новой среды исполнения |
| Совместимое расширение или provider | Интеграция среды исполнения и владелец пакета | Prepare, validate, publish, discard и drain в прежней сессии |
| Zero, native SDK или схема definition | Проверка выпуска | Новый согласованный набор зависимостей и проверка совместимости состояния. Не обычный `/reload` |

Основой служит существующий `packages/durable-reload`. Вторая реализация не нужна. Фабрика расширения хранит изменяемое состояние в экземпляре сессии, а не в общих переменных модуля. При горячей замене принятая работа сохраняет своего владельца и поколение. Новые вызовы используют опубликованный dispatch.

Механизм доставки memory и идентификаторы durable tasks не заменяются автоматически вместе с обычным инструментом. Ошибка `drain` после публикации не превращает `applied` в rollback. Транзакционность SQLite не гарантирует однократное выполнение внешних эффектов.

Штатный `openDurable()` ещё не предоставляет вызывающему коду полный lifecycle обновления. Вариант C предоставляет необходимые объекты через собственную композицию. Её корректность требует реальных тестов.

## 10. Поставка без скрытого форка

- Zero закреплён по версии, commit и контрольной сумме. Байты исходников и сборки не редактируются.
- Абсолютные импорты в `durable-zero/src`, aliases загрузчика, postinstall patches и обращения к private fields запрещены.
- Native-привязки имеют явные совместимые peer dependencies. Менеджер пакетов должен создать согласованный набор native-зависимостей. Независимые пакеты не должны незаметно загружать две версии native definitions или SDK.
- Необходимый native authorization patch отражается отдельно в manifest. Такой набор зависимостей не считается полностью штатным. Перенос patch в новый набор не выполнен. Этот документ не разрешает такой перенос.
- Минимальный Host не требует Hindsight, DeLM, BB, iii или HOME автора. Персональный профиль устанавливается отдельно.
- Уведомления MIT, сведения о происхождении и лицензии перенесённых компонентов сохраняются.
- Сервер определяет конфигурацию среды исполнения и доступ к credentials. Эти данные не входят в публичные DTO, fixtures или npm archive.

## 11. Первый проверяемый срез

Последовательность ниже описывает будущую реализацию. Она не создаёт новую DeLM-доску.

**Z0. Возможность реализации контракта.** Проверка неизменённого Zero охватывает публичные exports, упаковку, native-регистрацию пакетов и точный порядок запуска. Отдельно проверяются привязка до `resume`, среда исполнения и проверка полномочий перед commit. Для B требуется воспроизведение и устранение выявленных препятствий. Для C требуется отсутствие копий кода запуска и импортов внутренних модулей.

**Z1. Сквозной срез терминала.** Проверяется реальный путь от PTY терминала через SDK и Host к единственной композиции среды исполнения. Продолжение пути включает native SQLite, инструмент, ответ, отключение клиента и переподключение. Проверка использует временные сессии, faux provider и физическую изоляцию. Потеря подтверждения, отказ по scope, revoke и очистка проекции проверяются сразу, а не после демонстрации интерфейса.

**Z2. Пакеты и восстановление.** Срез подключает один простой пакет инструментов и один настоящий native-пакет с состоянием. Проверка охватывает повторное открытие, два разных экземпляра сессий, очистку и отсутствие повторных внешних эффектов. Затем проверяются memory, MCP, automation и DeLM по матрице EXTENSIONS.

**Z3. Интерфейс расширений и обновление.** Срез проверяет реальный обмен вводом и подтверждением, отключение клиента и повторный ответ. Отдельно проверяются замена занятого компонента, отклонение подготовки, `applied+drain-failed` и возврат совместимой версии. Пустые обработчики интерфейса и перезапуск не заменяют эти проверки.

**Z4. Потребители.** BB и iii подключаются к одному контракту SDK и Host. Их установка не включает движок исполнения. Проверка различает полномочия человека и delegated identity. Идентификатор той же сессии должен сохраняться.

**Z5. Общая приёмка.** Приёмка использует единый набор пакетов с контрольной суммой, чистую установку, автономные native-тесты и PTY. Она включает совместимость с закреплёнными клиентами, независимое ревью и QA. Исторические production gates не закрываются автоматически.

## 12. Проверяемые критерии исследования и реализации

| Проверка | Что покажет правильный результат | Текущее состояние |
|---|---|---|
| Zero immutable | Source/dist integrity неизменна; нет patch/deep import | Исследованный checkout чистый; product integration не существует |
| External registration | Реальный пакет ставит native definitions через public export | SOURCE подтверждён; registry unit tests 3 PASS; full native NOT RUN |
| Lifecycle | Ни один restored task не исполняется до обязательного bind | Для stock openDurable обнаружено несовпадение; C NOT RUN |
| Native authorization/env | Revoke после await не допускает commit; unsafe tools блокируются direct/nested | Предыдущий native REPORT; новый Zero closure NOT RUN |
| Package independence | Чистая установка и declarations не тянут private Host/Zero internals | NOT RUN |
| Single owner | Один Harness/Storage owner, безопасный concurrent attach | NOT RUN |
| Terminal | Ответ, инструмент, история и reconnect на реальном PTY | NOT RUN |
| Memory/DeLM | State identities, delivery/wake/dedupe и reload сохраняются | Старые component reports; Zero integration NOT RUN |
| BB/iii | Тот же Host/SDK, нет второго runtime, права сохранены | Спроектировано; NOT RUN |
| UI | Нет автоматического согласия и replay после reconnect | Спроектировано; NOT RUN |

Матрица сохраняет смысл DM-A–DM-G и ISC-79–85. Она не закрывает новые критерии ISA и не меняет исторические доказательства.

## 13. Итог

Отдельные пакеты и неизменённый Zero совместимы как архитектурное направление. Полный текущий Host требует внешней композиции C либо дополнительных возможностей готового владельца исполнения Zero. Исследованный API этих дополнительных возможностей не предоставляет.

До реализации необходимо согласовать границу запуска. Терминал, права, сохранение истории и поддержка будущих клиентов уже заданы требованиями. Повторный выбор этих требований не нужен.
