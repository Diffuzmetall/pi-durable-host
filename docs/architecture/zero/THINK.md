# THINK — как сохранить Zero неизменённым и не потерять Host

## 1. Решающий вопрос

Не «можно ли поместить код в npm-пакет», а **кто имеет право собрать runtime, установить политики и связать сервисы до начала восстановления задач**.

Факты из [OBSERVE](OBSERVE.md) допускают внешнюю регистрацию definitions. Они не доказывают, что готовый `openDurable()` даёт все точки управления нашим полным профилем.

## 2. Уточнённые предположения

| Предположение | Проверка | Решение |
|---|---|---|
| Для native packages нужно сначала менять Zero | `OpenDurableOptions.builtins` уже есть | Отвергнуто: регистрацию можно вынести сейчас |
| Отдельный пакет автоматически независим от runtime version | Native tasks/hooks/docs импортируют SDK | Отвергнуто: package boundary и compatibility boundary различаются |
| После `openDurable` успеем привязать сервисы | `resume()` предшествует return | Не принимать как доказательство безопасного reopen |
| Всё наше — стандартные Pi Extensions | Memory/automation используют Harness, Storage и native definitions | Разделить обычные Pi entrypoints и native composition |
| README про multi-client решает grants/UI/reconcile | В нём нет этих контрактов | Сохранять наш Host contract и отдельно проверять реализацию |
| Один Host обязательно означает один JS heap | Stock CodeMode имеет module-global sandbox | Процессы выбирать по изоляции, не по количеству пакетов |
| No-fork Zero означает stock всего dependency closure | Наш native-session требует authorization patch | Явно различать эти ограничения |
| `prompt()` ACK заменит наши receipts | Facade возвращает void; наш контракт хранит admission identity | Не ослаблять семантику ради подключения |

## 3. Варианты

| Вариант | Zero изменяется? | Наш полный профиль | Основная цена | Вывод |
|---|---|---|---|---|
| A. Запустить CLI/daemon Zero, Host сделать proxy | Нет | Не доказан: bootstrap скрыт, протокол слабее нашего | IPC плюс адаптация gaps, lifecycle и UI | Не выбирать основным путём |
| B. Встроить `openDurable({builtins})` в наш integration package | Нет | Частично: definitions да, обязательный bind-before-resume/env/authorization — нет | Самый малый код, но blockers нельзя спрятать | Хороший feasibility/minimal slice, не полный результат |
| C. Внешняя композиция exported Zero components и native SDK | Нет | Архитектурно позволяет сохранить наши owning boundaries; runtime ещё не проверен | Собственная композиция, которую уже частично имеет Host | Рекомендуется для полного профиля при библиотечном понимании Zero |
| D. Fork/patch Zero ради нужных callbacks | Да | Потенциально | Сопровождение fork | Исключён пользователем |
| E. Monkey-patch loader/Harness, deep imports, заменить singleton через глобальный cache | Формально source может остаться прежним, фактически контракт подменяется | Неустойчиво и небезопасно | Скрытый fork без контроля | Исключён |
| F. Оставить наш runtime и рядом открыть Zero на той же session | Нет | Нарушает единственного owner | Два открытия/планировщика/политики | Исключён |

### Важная честность о варианте C

C — это **не** вызов `DurableEngine.open()` с волшебным внешним плагином. Zero служит библиотекой повторно используемых компонентов, а наш integration package владеет композиционным root. Единственный execution engine остаётся native Pi Durable.

Не копируем `runtime-loader.ts`, не переносим его код под нашим именем и не открываем второй Harness. Используем текущую композицию Host и только подходящие публичные exports Zero. Отсутствующий общий bootstrap не выдаём за готовую функцию Zero.

Если пользователь считает обязательным именно готовый runtime owner Zero, а не его публичные компоненты, **C не удовлетворяет этому дополнительному условию**. Тогда при сохранении всех прежних гарантий вариант B имеет выявленные blockers; требуется подходящий upstream release либо отдельное согласование изменения требований. В этом исследовании таких разрешений не предполагаем.

## 4. Рекомендация

Проектировать единый внешний пакет `@dpi/runtime-zero` и независимые capability packages. Для полного профиля использовать вариант C, но до начала переноса явно зафиксировать именно это значение «основываться на Zero».

Вариант B проверить малым изолированным экспериментом как возможность более дешёвой реализации. Не поставлять B и C одновременно как два переключаемых runtime. Если B не сохраняет обязательные свойства, не оставлять его скрытым fallback и не объявлять частичный профиль полноценным.

Библиотечный package integration — не бессодержательная обёртка: он скрывает native lifecycle, транзакционную admission, безопасную проекцию и compatibility от Host/SDK. Эти обязанности уже определены DM1.

## 5. Минимальные границы пакетов

- **Host/backend:** клиентская authentication, grants, каталог и транспорт.
- **Runtime integration:** один native owner, разрешённая композиция, bind/resume/close, receipts, projection и reload.
- **Capability packages:** memory, MCP/guards, automation, DeLM, tools/providers. Каждый содержит свою логику и необходимые узкие native bindings.
- **Profile:** доверенный composition root, выбирающий конкретные пакеты и конфигурацию. Это существующий смысл runtime profile, не новый универсальный plugin SDK.
- **SDK и адаптеры:** публичный wire; terminal/BB/iii не импортируют Zero, native SDK или серверные extension packages.

Не создавать отдельный пакет на каждый инструмент или файл. Пакет выделяется, когда ему нужны собственные установка, lifecycle, optional dependency либо совместимость.

## 6. Внешние packages не означают remote plugins

Расширения — доверенный серверный код. Они работают рядом с единственным runtime и могут иметь native definitions. Ни QuickJS CodeMode, ни разделение npm packages не делают Node extension безопасным для загрузки от недоверенного клиента.

Нельзя превратить DeLM/Goal/memory delivery в сеть независимых сервисов с отдельными scheduler/DB только ради слова «внешние». Внешний пакет отделён по поставке, но его native состояние остаётся в той же session.

Чистая прикладная логика не импортирует Zero/Host. Native bindings могут импортировать квалифицированный native SDK; это явная зависимость, не нарушение само по себе. Клиентский контракт при этом остаётся независимым.

## 7. Вопросы, которые нельзя решить упаковкой

### Before-resume и исходный Storage

Memory/automation связываются с правильной session до запуска восстановленных задач. Поздний bind и немедленный pause не равнозначны этому порядку. Получение второго Storage handle не заменяет исходный Storage lifecycle owner.

### Security fences и execution environment

Проверка токена на HTTP-входе не заменяет проверку перед native commit после await. Обычный prompt hook не заменяет DCG environment. Запрет direct tool не гарантирует запрета nested CodeMode call.

### UI

Для наших адаптируемых пакетов можно передать небольшой callback-port UI запросов. Для произвольного стороннего Pi UI нужен полноценный поддержанный bridge. `custom(renderFunction)` не сериализуется в JSON и не выполняется автоматически в BB/browser.

### Reload

Повторная регистрация или закрытие/open сессии не равны hot reload. Необходимо сохранить definitions, state, владельцев подписок и semantics «publication applied, drain failed». Внешний reload package может владеть этим только при наличии нужных native handles и правильного lifecycle.

### Default integrations

При внешней композиции выбираем одного владельца subagent, CodeMode и MCP. Не запускаем stock MCP loader и наш policy manager одновременно для тех же источников. Не создаём два инструмента с одним именем или competing controller.

## 8. Что принять из архитектурных правил

Применён `arch / clean-architecture`:

1. Политики и capability logic не должны зависеть от способа подключения terminal/BB/iii.
2. Native representations заканчиваются в runtime adapter; наружу идут обычные request/result модели.
3. Конкретная сборка зависимостей принадлежит composition root, а не каждому extension.
4. Package/declaration checks должны подтверждать границы. Одна диаграмма не является доказательством.
5. Сохраняем существующие проверки и поведение при изменении направления зависимостей; не заменяем security инварианты более удобным API.

## 9. Связь с DM1 без переписывания истории

| Раньше | После предлагаемой адаптации |
|---|---|
| Глубокий runtime-модуль внутри backend | Его контракт сохраняется; реализация выделяется в внешний runtime-zero package |
| Native bindings внутри `native-profile` | Переезжают вместе со своими capability owners в отдельные packages |
| SDK и terminal/iii без native imports | Сохраняется; BB получает ту же границу позже |
| Полный профиль как внутренняя сборка Host | Отдельно устанавливаемый trusted profile с optional capabilities |
| `packages/durable-reload` | Переиспользуется/адаптируется к новому composition owner, не заменяется второй системой |
| DM-A–DM-G, ISC-79–85 | Смысл сохраняется; принятие нового package tuple требует новых checks |
| Исторические FAIL и ограничения production | Не изменяются |

Это предложение для следующего плана. Не пересоздавать tasks, не менять claims работающих агентов и не объявлять DM1 завершённым этим документом.

## 10. Что должно опровергнуть рекомендацию

- Если публичный `openDurable` на выбранной неизменённой версии обеспечивает все необходимые pre-resume/env/authorization/UI точки, вариант B дешевле C и должен победить. Сейчас SOURCE показывает обратное для ключевых options.
- Если C требует скопировать большую часть Zero bootstrap или использовать private imports, не называть его чистой интеграцией. Остановить эту ветвь и пересмотреть основу.
- Если пакет переносит логику в клиента или создаёт второй execution owner, он нарушает исходную цель.
- Если изменения Zero необходимы для первого обязательного инварианта и нет внешнего публичного пути, результат — точный blocker, не скрытый patch.

Итог THINK: внешний package layout пригоден; выбранный способ bootstrap является отдельным архитектурным решением. Его честная граница и проверочные сценарии описаны в [ARCHITECTURE](ARCHITECTURE.md).
