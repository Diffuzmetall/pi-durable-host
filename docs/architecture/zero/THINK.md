# THINK: сохранение Zero и гарантий Host

Назначение по Diátaxis: объяснение вариантов и рекомендуемой архитектуры.

## 1. Кто собирает runtime до восстановления задач

Главный вопрос касается полномочий и lifecycle, а не возможности поместить код в npm-пакет. Кто собирает runtime, устанавливает политики и привязывает сервисы до начала восстановления задач?

Факты из [OBSERVE](OBSERVE.md) подтверждают внешнюю регистрацию native definitions. Они не подтверждают, что готовый `openDurable()` предоставляет все точки управления нашим полным профилем.

## 2. Предположения и основания решений

| Предположение | Проверенный факт | Вывод |
|---|---|---|
| Native packages сначала требуют изменения Zero | `OpenDurableOptions.builtins` уже существует | Регистрацию можно вынести сейчас |
| Отдельный пакет независим от runtime version | Native tasks/hooks/docs импортируют SDK | Граница поставки пакета не совпадает с границей совместимости |
| Сервисы можно безопасно привязать после `openDurable` | `resume()` выполняется до return | Поздняя привязка не доказывает безопасный reopen |
| Все наши расширения являются стандартными Pi Extensions | Memory/automation используют Harness, Storage и native definitions | Нужны отдельные обычные Pi entrypoints и native composition |
| README о multi-client определяет grants/UI/reconcile | README не содержит этих контрактов | Наш Host contract сохраняется и проверяется отдельно |
| Один Host обязательно означает один JS heap | Штатный CodeMode имеет module-global sandbox | Изоляция определяет процессы, а число пакетов её не определяет |
| Запрет fork Zero запрещает изменения всех зависимостей | Наш native-session требует authorization patch | Это разные ограничения |
| ACK от `prompt()` заменяет receipts | Facade возвращает void, а наш контракт сохраняет admission identity | Подключение не оправдывает ослабление семантики |

## 3. Варианты интеграции

| Вариант | Изменение Zero | Полный профиль Host | Цена и вывод |
|---|---|---|---|
| A. CLI/daemon Zero с Host как proxy | Нет | Не доказан. Bootstrap скрыт, протокол слабее нашего | IPC, недостающие контракты, lifecycle и UI требуют адаптации. Не основной путь |
| B. `openDurable({builtins})` во внешнем пакете интеграции | Нет | Частичный. Есть definitions, но нет обязательных bind-before-resume/env/authorization | Кода меньше всего, но препятствия сохраняются. Подходит для минимального эксперимента, не полного результата |
| C. Внешняя композиция публичных компонентов Zero и native SDK | Нет | Архитектура позволяет сохранить владельцев и границы Host. Выполнение не проверено | Нужна собственная композиция, частично существующая в Host. Рекомендуется при библиотечном понимании Zero |
| D. Fork/patch Zero для нужных callbacks | Да | Потенциально возможен | Требует сопровождения fork. Пользователь исключил этот вариант |
| E. Monkey-patch loader/Harness, deep imports или замена singleton через глобальный cache | Формально source может остаться прежним, но контракт подменяется | Неустойчив и небезопасен | Скрыто изменяет зависимость без контроля. Исключён |
| F. Наш runtime и отдельный Zero на той же session | Нет | Нарушает требование единственного владельца | Дважды открывает состояние и создаёт два планировщика и набора политик. Исключён |

### 3.1. Что означает вариант C

Вариант C не означает вызов `DurableEngine.open()` с внешним плагином, который решает все ограничения. Zero предоставляет повторно используемые компоненты. Наш пакет интеграции выбирает зависимости и собирает runtime. Единственным движком выполнения остаётся native Pi Durable.

Этот вариант использует текущую композицию Host и только подходящие публичные exports Zero. Он не копирует `runtime-loader.ts`, не переносит его код под нашим именем и не открывает второй Harness. Отсутствующая общая функция запуска не считается готовой функцией Zero.

Если пользователь требует готового runtime owner Zero, а не его публичных компонентов, вариант C не удовлетворяет дополнительному условию. При сохранении прежних гарантий вариант B имеет выявленные препятствия. Тогда нужен подходящий upstream release или отдельное согласование изменения требований. Исследование не предполагает такого согласования.

## 4. Рекомендация для полного профиля

Рекомендуется единый внешний пакет `@dpi/runtime-zero` и независимые пакеты возможностей. Для полного профиля рекомендуется вариант C. До переноса необходимо явно согласовать библиотечное значение требования «основываться на Zero».

Вариант B остаётся кандидатом для малого изолированного эксперимента с потенциально меньшей ценой реализации. B и C не должны поставляться одновременно как два переключаемых runtime. Если B не сохраняет обязательные свойства, он не должен оставаться скрытым резервным путём. Частичный профиль не становится полноценным.

Пакет интеграции скрывает от Host и SDK native lifecycle, транзакционную admission, безопасную проекцию и проверку совместимости. Эти обязанности уже определены DM1.

## 5. Границы пакетов и владельцев

Каждый слой имеет отдельные обязанности:

- Host/backend отвечает за аутентификацию клиентов, grants, каталог и транспорт.
- Runtime integration содержит одного native owner, допустимую композицию, bind/resume/close, receipts, projection и reload.
- Пакеты возможностей содержат memory, MCP/guards, automation, DeLM и tools/providers. Каждый пакет включает свою логику и необходимые узкие native bindings.
- Profile является доверенным composition root. Он выбирает пакеты и конфигурацию, но не создаёт универсальный plugin SDK.
- SDK и адаптеры используют публичный протокол. Terminal, BB и iii не импортируют Zero, native SDK или серверные пакеты расширений.

Отдельный пакет не нужен для каждого инструмента или файла. Основанием служат собственная установка, lifecycle, необязательная зависимость или требования совместимости.

## 6. Внешний пакет остаётся серверным кодом

Расширения являются доверенным серверным кодом рядом с единственным runtime. Они могут содержать native definitions. QuickJS CodeMode и разделение npm-пакетов не делают Node extension безопасным для загрузки от недоверенного клиента.

Внешняя поставка не требует превращать DeLM, Goal и memory delivery в независимые сервисы с отдельными планировщиками и БД. Их native состояние остаётся в той же session.

Чистая прикладная логика не импортирует Zero или Host. Native bindings могут импортировать проверенный на совместимость native SDK. Это явная зависимость, а не нарушение само по себе. Клиентский контракт остаётся независимым.

## 7. Ограничения, которые упаковка не устраняет

### 7.1. Привязка до resume и исходный Storage

Memory и automation привязываются к правильной session до запуска восстановленных задач. Поздний bind с немедленным pause не равнозначен этому порядку. Второй Storage handle не заменяет исходный lifecycle владельца Storage.

### 7.2. Авторизация и среда исполнения

Проверка токена на входе HTTP не заменяет проверку перед native commit после await. Обычный prompt hook не заменяет среду DCG. Запрет direct tool не гарантирует запрета nested CodeMode call.

### 7.3. Пользовательский интерфейс

Наши адаптируемые пакеты могут принимать небольшой интерфейс callbacks для запросов UI. Произвольный сторонний Pi UI требует полноценного поддерживаемого bridge. `custom(renderFunction)` не сериализуется в JSON и автоматически не выполняется в BB или браузере.

### 7.4. Reload

Повторная регистрация или закрытие и открытие сессии не равны hot reload. Необходимо сохранить definitions, state, владельцев подписок и semantics «publication applied, drain failed». Внешний reload package может отвечать за это только с нужными native handles и правильным lifecycle.

### 7.5. Штатные интеграции

Внешняя композиция выбирает одного владельца subagent, CodeMode и MCP. Штатный MCP loader и наш policy manager не должны одновременно обслуживать те же источники. Два инструмента с одним именем или конкурирующие controllers также недопустимы.

## 8. Архитектурные правила

В исходной работе применён `arch / clean-architecture`. Из него приняты следующие правила:

1. Политики и логика возможностей не зависят от способа подключения terminal, BB или iii.
2. Native representations заканчиваются в runtime adapter. Клиент получает обычные request/result модели.
3. Composition root собирает конкретные зависимости. Отдельные расширения не собирают runtime заново.
4. Проверки packages и declarations подтверждают границы. Одна диаграмма их не доказывает.
5. Изменение направления зависимостей сохраняет прежние проверки и поведение. Удобство API не заменяет инварианты безопасности.

## 9. Связь предложения с DM1

| Прежняя архитектура | Предлагаемая адаптация |
|---|---|
| Глубокий runtime-модуль внутри backend | Контракт сохраняется. Реализация выделяется во внешний runtime-zero package |
| Native bindings внутри `native-profile` | Переносятся вместе со своими владельцами возможностей в отдельные пакеты |
| SDK и terminal/iii без native imports | Граница сохраняется. BB получает её позже |
| Полный профиль как внутренняя сборка Host | Отдельно устанавливаемый доверенный profile выбирает необязательные возможности |
| `packages/durable-reload` | Повторно используется или адаптируется к новому composition owner. Вторая система не создаётся |
| DM-A–DM-G, ISC-79–85 | Смысл сохраняется. Новый набор версий пакетов требует новых проверок |
| Исторические FAIL и ограничения production | Не изменяются |

Это предложение для следующего плана. Оно не пересоздаёт tasks, не меняет claims действующих агентов и не завершает DM1.

## 10. Условия пересмотра рекомендации

Рекомендация изменится при следующих результатах:

- Если публичный `openDurable` неизменённой версии обеспечивает все необходимые pre-resume/env/authorization/UI точки, B дешевле C и должен получить предпочтение. Сейчас SOURCE показывает обратное для ключевых options.
- Если C требует копировать большую часть bootstrap Zero или использовать private imports, этот вариант нельзя считать чистой интеграцией. Тогда необходимо остановить эту ветвь и пересмотреть основу.
- Если пакет переносит логику в клиента или создаёт второго владельца выполнения, он нарушает исходную цель.
- Если первый обязательный инвариант требует изменения Zero без публичного внешнего пути, результатом остаётся точное препятствие, а не скрытый patch.

Внешняя структура пакетов пригодна, но способ запуска остаётся отдельным архитектурным решением. [ARCHITECTURE](ARCHITECTURE.md) описывает его границы и проверочные сценарии.
