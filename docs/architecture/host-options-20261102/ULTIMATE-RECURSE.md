## Компоненты полезны, полная замена пока не обоснована

Оба проекта следует рассматривать как источники компонентов, а не как готовую замену нашего Host. Ultimate является предпочтительным резервным кандидатом для отдельного прототипа полной серверной основы. Он использует Durable 1.5 и предоставляет развитый жизненный цикл расширений.

Recurse полезнее как источник реализации файлов, фоновых процессов и координации агентов. Его стабильная версия использует Durable 1.3 и внутренние импорты Pi.

Подключить наш терминал, BB или iii вместо браузера технически возможно у обоих кандидатов. Выполнение принадлежит серверу, а клиенты обращаются через HTTP и SSE. Однако dpi-sdk несовместим с их протоколами. Нужен серверный адаптер контрактов, а не только другой код отображения.

Обход браузера через существующий API не требует удаления UI или изменения движка. Физическое удаление UI из поставки не даёт поддерживаемую библиотеку без интерфейса одним переключателем. У Ultimate загрузчик расширений связан с Vite. Recurse собирает и обслуживает веб-приложение вместе с сервером. Документированный независимый headless SDK не найден.

> 🧠 **From Hindsight memory (Component map)** — наш backend владеет выполнением, admission и durable state; адаптеры не должны создавать второй runtime.

Эта граница также описана в `/var/tmp/pi-host-public-20261102-9zu17ezn/repo/docs/architecture/MAP.md`. Карта отличает существующую реализацию от предложения Zero. Матрица `zero/EXTENSIONS.md` описывает будущую упаковку, а не готовые пакеты.

## Изоляция данных не доказывает изоляцию пользователей

Оба кандидата разделяют разговоры на уровне данных и native ownership. Изоляция недоверенных пользователей средствами ОС не подтверждена. NodeExecutionEnv Ultimate и группы процессов Recurse не следует считать такой изоляцией. Модельный safety review Recurse также не заменяет наши детерминированные grants и guards.

## Три ограничения определяют цену адаптера

1. Ultimate оставляет неопределённость после потери ACK. Submit DTO не принимает клиентский requestId, а submissionId клиент получает только в ответе сервера. Повтор POST может создать другое выполнение. Клиентский журнал сам по себе этого не исправляет.
2. Ограниченный API Recurse не предоставляет нужный путь адаптера. Service endpoint разрешает только content, без client_message_id и attachment_ids. Операторский доступ или backend key расширяет полномочия и требует отдельного решения.
3. Recurse может отправить текст без изображения. Лимит объёма prompt и ошибки обработчика исключают image blocks. Нашему контракту нужен явный результат обработки вложений либо отказ в допуске сообщения.

Это выводы по исходникам, а не результаты воспроизведения. Отсутствие открытых GitHub issues не означает отсутствие дефектов. Подробные основания и immutable ссылки сохранены в [справочнике](REFERENCE.md).

## Подключение клиента и перенос истории являются разными задачами

Без fork можно запустить штатное приложение и подключить внешний клиент к существующему API. Ultimate также поддерживает проектные серверные расширения. Однако гарантированный receipt требует публичной native транзакционной возможности либо изменения HTTP admission. В Recurse расширение service DTO и реестра в исходниках требует собственного patch или fork.

У обоих кандидатов можно сохранить выбранные протоколы MCP и часть схем инструментов. Общее происхождение от Pi облегчает адаптацию native definitions, но не доказывает бинарную совместимость. Учётные данные, model IDs и policies должны оставаться серверными и проходить явную проверку.

Полная замена автоматически не сохраняет следующие контракты и данные:

- dpi-sdk DTO, SSE projection, receipts/fingerprints с привязкой к субъекту, grants и parent authority;
- Hindsight native docs/tasks и delivery kernel, Goal/schedules, DeLM binding и guards;
- reload prepare/publish/drain, callback ports и существующие терминальные widgets;
- BB bindings, неизменяемые answer references, версии task/document и соответствия provider identity.

Замена UI не требует миграции истории. Замена владельца выполнения требует отдельного проекта миграции. Историю сообщений можно переносить как архив с указанием происхождения. Архив нельзя считать исполняемым продолжением native задач.

Нельзя автоматически копировать активные SQLite, незавершённые инструменты, учётные данные OAuth и binding IDs между этими приложениями. Общее семейство Durable не делает равными registry, namespaces, версии и среду восстановления.

## Цена интеграции и поддерживаемость

Клиентский прототип Ultimate относительно прямой благодаря общим HTTP/SSE и native documents. Полная интеграция требует receipts, grants, адаптации связанного с Vite загрузчика и переноса нашего native profile. Durable 1.5 и готовый lifecycle reload облегчают такую работу. Однако стабильных выпусков нет. Автор не обещает совместимость и миграции, а зависимости содержат patches.

У Recurse быстрее исследовать компоненты файлов, вложений и восстановления процессов. Полная замена без зависимости от UI требует преобразования протокола и изменения service API. Также нужны перенос с Pi 1.3 и отказ от deep imports. Его преимущества включают закреплённый выпуск, отдельные службы маршрутов и service principals. Ограничения включают расширения в исходниках, patches и отсутствие публичной истории сопровождения после первого выпуска.

Рекомендуется оставить текущего владельца выполнения и заимствовать отдельные компоненты после проверки лицензий и lifecycle. Если нужен сравнительный прототип Host, первым кандидатом остаётся Ultimate на закреплённом commit. Перенос истории и активных задач не входит в такой прототип. [Предложение проверки](CHECK-PROPOSAL.md) описывает минимальный эксперимент после отдельного разрешения на запуск.
