# Какую серверную основу выбрать

[Оглавление исследования](README.md) · [Сравнение фактов](COMPARISON.md) · [Источники и проверки](EVIDENCE.md)

## Рекомендация

**Первым стоит проверить Pi Pocket как готовый backend для нового изолированного прототипа.** Он уже принимает изображения, обслуживает нескольких клиентов и восстанавливает native-задачи. Его браузерный интерфейс можно не использовать.

**Для сохранения полного нынешнего профиля разумнее пока оставить наш Host.** Ни один кандидат не сохраняет без доработок наши права, повторные запросы, расширения и BB-привязки. Это основание сохранить серверный контракт, а не оправдание текущей сложности или незаконченной миграции.

Опубликованный снимок нашего Host не принят как релиз. Его backend и terminal не прошли прежний typecheck. [Статус снимка](../STATUS.md) сохраняет эти ограничения. Рекомендация не означает установку этого снимка на рабочий сервер.

**Ultimate стоит держать вторым кандидатом**, если важнее основа на Durable 1.5 и развитый механизм обновления расширений. Но это не более простая готовая замена. Его сервер связан с Vite, а API отправки не использует клиентский `requestId`.

Выбор зависит от того, какие собственные функции мы готовы заменить функциями кандидата. Ни меньший HTTP-сервер, ни отсутствие Express сами по себе не уменьшают стоимость всей системы.

## Pi Pocket сокращает работу, если принять его модель приложения

Pocket предоставляет сервер, изображения, историю, подагентов, задачи по расписанию и загрузку native-расширений. Модель исполняется на сервере. Наш терминал или BB могут обращаться к HTTP API вместо браузера.

В этом варианте мы принимаем Pocket как приложение, а не пытаемся незаметно превратить его в прежний Host. Вместо части собственных функций мы используем функции Pocket. Совпадение названий Goal или memory не означает совпадения поведения.

Собственная работа остаётся в следующих областях:

- адаптер протокола для терминала, BB и iii;
- отображение ролей клиента в права Pocket;
- подтверждение повторных запросов и безопасное создание сессии после потери ответа;
- строгая проверка метаданных вложений;
- нужные native-расширения, включая MCP и Hindsight;
- отдельный перенос истории, если он нужен.

Pocket использует Durable 1.4.0. Его `pocket.sqlite` содержит несколько сессий в одном Harness. Наш Host открывает отдельные session storage и Harness. Поэтому одинаковая версия движка не делает базы взаимозаменяемыми.

Обычные Pi extensions не соответствуют контракту Pocket. В стабильном upstream исследователь не нашёл встроенного MCP bridge. Локальный checkout 0.26.0 содержит дополнительные изменения, которых нет в чистом upstream.

**Условие выбора Pocket:** согласиться на его модель приложения и доказать нужный клиентский контракт на новом стенде. Если поверх Pocket приходится восстанавливать почти весь наш Host, ожидаемая экономия исчезает.

Подробности находятся в [отчёте Pi Pocket](PI-POCKET.md).

## Ultimate ближе к целевой версии движка, но требует изменения API

Ultimate использует Durable 1.5.0. В исходниках есть входные изображения, MCP, native-расширения и lifecycle с привязкой ресурсов до `resume()`.

Для этой цели Ultimate ближе к готовому серверному приложению, чем выборочная сборка библиотек Zero. Но близость версии не означает совместимость наших полномочий, документов и задач.

Главное ограничение находится в `conversation.submit`. HTTP-обработчик не передаёт туда клиентский `requestId`. После потери ответа клиент не получает надёжного способа повторить прежнее намерение. Исправить это только журналом клиента нельзя.

Есть и дополнительные издержки. Основной запуск создаёт Vite, а загрузчик расширений использует его модули и watcher. Стабильных тегов нет. Автор предупреждает о фундаментальных изменениях без миграций.

**Условие выбора Ultimate:** принять поддержку серверной адаптации и сначала закрыть повторную отправку. Он подходит для исследования новой основы на 1.5, но пока не выигрывает как неизменяемая готовая зависимость.

Доказательства приведены в [отчёте Ultimate и Recurse](ULTIMATE-RECURSE.md).

## Recurse полезнее частями

Recurse уже содержит обработку вложений, управление фоновыми процессами, дерево агентов и MCP. Эти решения полезны для сравнения с нашим кодом.

Однако два его API дают разные возможности. Operator API принимает идентификатор сообщения и вложения. Ограниченный service API принимает только `content`.

Поэтому подключение BB или iii через ограниченные полномочия сразу теряет часть нужного контракта. Использование операторских прав вместо service API не решает эту проблему безопасно.

Стабильная версия Recurse использует Durable 1.3.0 и внутренние импорты Pi. Полная замена перенесёт к нам ещё одну сложную композицию. **Для нынешней задачи я предпочитаю изучать отдельные решения Recurse**, прежде всего вложения и восстановление процессов.

## Components расширяет Host, но не заменяет его

`pi-durable-components` предоставляет библиотеки с явными точками регистрации и lifecycle. Они получают существующие Harness и Storage от приложения.

Это подходящее направление для сокращения собственного кода отдельных функций. Но набор не предоставляет готовый общий сервер с нашими правами, API и журналом подтверждений.

Готовые исследованные версии нельзя считать совместимой комбинацией. Components 0.10.0 требует Durable 1.4.0, а Zero 0.7.0 требует 1.5.0. Кроме того, stateful-компонентам нужна привязка до `resume()` и исходный Storage.

**Рекомендация:** выбирать конкретный компонент и проверять его отдельно. Не устанавливать весь набор ради одного инструмента. Не создавать второй экземпляр движка для обхода несовместимых зависимостей.

Основание приведено в [отчёте SRE Agent и Components](SRE-COMPONENTS.md).

## Cloudflare и AgentRun решают другие задачи размещения

Cloudflare sample показывает восстановление native-задач через Durable Objects, SQLite и alarms. Он полезен, если целью становится размещение на Cloudflare.

Для нашего VPS это не упрощение без дополнительных условий. Потребуется другой инфраструктурный слой и отдельное защищённое исполнение локальных инструментов. В sample нет авторизации и готового входного пути изображений.

AgentRun Server может работать на VPS с локальными данными и дочерним процессом на run. Управляемые Render или Archil ему не обязательны. Его полезные отличия относятся к изоляции запусков, workflow и учёту неопределённых внешних эффектов.

Но исследованный Serve допускает Durable только ниже 1.4. В обработчике подтверждений найдено окно между выполнением операции и сохранением ключа повторного запроса. После сбоя повтор может получить новый native ID. Этот вывод подтверждён исходниками, но не проверен аварийным тестом.

**Рекомендация:** брать у этих проектов подходящие решения, а не менять ради них весь Host. AgentRun стоит рассмотреть целиком только при переходе к модели agents и runs вместо нашего нынешнего контракта сессий.

Подробности находятся в [отчёте Cloudflare и AgentRun](CLOUDFLARE-AGENTRUN.md).

## SRE Agent не подходит на роль общего Host

SRE Agent содержит полезный пример восстановления инцидента и подтверждений человека. Но его API обслуживает один тип задачи, а не общий каталог агентных сессий.

Общий Host потребует дописать почти все нужные серверные функции. Лицензия приложения также не установлена. **Вариант исключён из списка основ для замены**, но остаётся примером для изучения.

## Где остаётся Zero

Предыдущий [вариант Zero](../zero/ARCHITECTURE.md) остаётся допустимой архитектурной гипотезой. Публичные библиотеки Zero можно исследовать для внешней композиции, не меняя сам Zero.

Это отличается от установки готового `openDurable()` вместо нашего Host. Нужные полномочия, lifecycle, клиенты и совместимость расширений всё равно должен обеспечить владелец приложения.

**Если главное требование состоит в готовом backend, сначала проверять стоит Pocket.** Если важнее собственная композиция, сравнивать следует наш `DurableSession` с выборочными библиотеками Zero. В обоих вариантах нужно определить одного владельца native API.

Новое исследование не утверждает реализацию варианта Zero и не отменяет действующую работу по DM1.

## Что BB меняет в выборе

Наличие HTTP или SSE не означает готовую интеграцию BB. Наш адаптер требует точной привязки Root и children, серверных полномочий и согласованной истории.

Для текущего Host путь уже определён в исходниках:

```text
BB Core → dpi-bb-provider → dpi-sdk → Host → Durable
```

При выборе Pocket или Ultimate меняется серверный протокол за адаптером. Сам BB не должен становиться вторым исполнителем той же задачи. Iframe с web-интерфейсом кандидата не заменяет provider adapter.

[Контракт BB-адаптера](../BB-ADAPTER.md) описывает существующие настройки и ограничения. Пунктир в [общей схеме](../README.md) обозначает, что полная интеграция ещё не принята.

## Следующая проверка должна решить вопрос о замене

Первый эксперимент с Pocket имеет смысл только на новой базе и без production-credentials. Стенд должен физически исключать доступ к рабочим базам и секретам. Одной замены `HOME` недостаточно.

Эксперимент должен проверить не красоту интерфейса, а три свойства.

1. Один клиент отправляет изображение, другой видит сохранённое сообщение. Модель получает image block, а ошибка обработки видна клиенту.
2. После потери ответа повтор сохраняет прежнее намерение. Изменение текста под тем же идентификатором вызывает конфликт.
3. После перезапуска восстанавливаются задача, права и история. Отзыв доступа прекращает чтение и новые изменения.

Затем можно проверить один native-модуль нашего профиля и минимальную привязку BB. Если для этого требуется новый сервер внутри Pocket, замену следует отклонить как неупрощающую архитектуру.

Эти проверки предложены, но не выполнены. Производительность кандидатов, потребление памяти и стоимость эксплуатации не измерялись.
