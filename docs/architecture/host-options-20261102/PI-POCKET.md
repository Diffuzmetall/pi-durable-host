# Pi Pocket как сервер нашего Host

Этот документ объясняет выбор серверной части. [Справочник](POCKET-REFERENCE.md) содержит версии, матрицу возможностей, API, путь изображений и настройки.

[Проверочный эксперимент](POCKET-EXPERIMENT.md) описывает будущие действия. Новое исследование и runtime-проверки при редактуре не проводились.

## Вывод

**Оставить Pocket резервным вариантом замены всей серверной части.** Pi Pocket подходит для отдельного проверочного прототипа. Один сервер исполняет задачи, а несколько клиентов подключаются через HTTP. Входные изображения уже проходят до модели.

Однако Pocket не обеспечивает совместимую замену нашего backend. У него другие API, авторизация, документы и состав расширений. Готового адаптера BB в upstream не найдено.

Pi Pocket не заменяет Durable другим движком. Это готовое многопользовательское приложение поверх **Pi Durable 1.4.0**, с собственным сервером и мобильным web-интерфейсом. Главное преимущество Pocket состоит в готовом составе приложения. Преимущество движка, скорости или памяти не доказано.

## API без web-интерфейса

`src/server/main.ts` создаёт HTTP-сервер Node. `http.ts` маршрутизирует API отдельно от статических файлов web. `PocketApp` владеет исполнением, а HTTP вызывает его методы. Поэтому наш терминал, BB и iii могут работать без открытия Pocket UI.

Отказ от использования web и удаление UI из поставки требуют разных изменений. Клиент может работать без web и без fork. Удаление UI из поставки потребует изменить упаковку или точку запуска. Сервер содержит проекции и функции для своего приложения.

[Справочник API](POCKET-REFERENCE.md#http-api) перечисляет методы.

API принимает cookie или `Authorization: Bearer <token>`. Для всех методов, кроме GET, требуется `X-Pocket: 1`. Заголовок защищает от межсайтовой отправки форм, но не заменяет авторизацию.

Поток серверных событий, SSE, посылает именованные JSON-события, включая `hello` и `view`. В протоколе есть варианты проекции. Новые клиенты получают облегчённые записи и догружают контекст. При повторном подключении сервер формирует состояние заново.

Долговечного журнала SSE с `Last-Event-ID` не найдено. Запись содержит `event` и `data` без `id`. События long-poll имеют последовательность внутри временного обработчика опросов. Долговечного серверного курсора для них не найдено.

Адаптер обязан восстанавливать состояние из серверной истории и снимка состояния. Поток событий не является единственным журналом. Следует закрепить поддерживаемый протокол. Нельзя автоматически выбирать самую новую проекцию.

Источники: [маршрутизация HTTP](https://github.com/TannerMidd/pi-pocket/blob/50194aa38eb368ef2cb8599d44fba81b05ed5263/src/server/http.ts#L29-L43), [auth](https://github.com/TannerMidd/pi-pocket/blob/50194aa38eb368ef2cb8599d44fba81b05ed5263/src/server/auth.ts#L91-L107), [проверки API](https://github.com/TannerMidd/pi-pocket/blob/50194aa38eb368ef2cb8599d44fba81b05ed5263/src/server/http/api.ts#L128-L153), [SSE](https://github.com/TannerMidd/pi-pocket/blob/50194aa38eb368ef2cb8599d44fba81b05ed5263/src/server/http/events.ts#L55-L163), [проекция клиента](https://github.com/TannerMidd/pi-pocket/blob/50194aa38eb368ef2cb8599d44fba81b05ed5263/src/server/room.ts#L527-L555).

## Исполнение, восстановление и расширения

`PocketApp` открывает `ModelRuntime`, `CodingTools` и registry расширений. Затем открывает `pocket.sqlite`, создаёт `Harness`, восстанавливает проекции и вызывает `resume`. Файловая блокировка ограничивает экземпляр одним серверным процессом. Отказ общего процесса влияет на все сессии. Этот сервер не является горизонтально масштабируемым кластером.

Durable сохраняет transcript, задачи, документы и checkpoints. Например, schedules и PR watches используют `sleepUntil`. Страницы браузера, ожидание подтверждений tool calls и незавершённый вход провайдера относятся к состоянию процесса. Их восстановление нельзя приравнивать к восстановлению задачи.

Background-команды используют отдельные процессы и файлы вывода. Код проверяет их состояние через идентификатор процесса, группу процессов и идентификатор запуска операционной системы. Код явно допускает неизвестный результат после обрыва запуска. Такой результат точнее автоматического повторного запуска, но наш клиент должен корректно его отображать.

Расширение Pocket представляет собой модуль `.ts` с функцией `(host, web)` как default export. Эта функция возвращает Durable Extension либо список. Registry подключает native-инструменты, hooks, разделы prompt, задачи и документы. Web-часть необязательна. Обычный Pi ExtensionAPI не является этим контрактом.

Loader следит за файлами встроенных и внешних модулей, built-in и drop-in. Он заменяет регистрации и сохраняет прежнюю версию при ошибке загрузки. Cleanup закрывает ресурсы прошлой версии.

Обновление Pocket сохраняет drop-ins. Галерея закрепляет версии через commit и hash, предлагает ручное подтверждение обновлений. Такая загрузка не обеспечивает автоматическую совместимость любого расширения. Виды сохраняемых документов, имена задач и checkpoints должны оставаться совместимыми.

Зависимость `@earendil-works/pi-mcp` 1.4.0 присутствует в `package.json`, но встроенной регистрации MCP в `src` не найдено. Для MCP нужен отдельный native drop-in либо иной серверный bridge с управлением transport, credentials и cleanup. Нельзя считать наличие npm-зависимости готовым подключением MCP.

Модели и авторизация провайдеров остаются серверными, через Pi ModelRuntime и `~/.pi/agent/auth.json`. Расширения также исполняются с правами владельца сервера. Pocket реализует собственную функцию памяти. Она не является готовой заменой Hindsight. Локальный checkout содержит отдельную Hindsight-адаптацию, которой нет в исследованном стабильном upstream.

## BB через адаптер

Рекомендуется подключать BB через наш серверный адаптер к HTTP API Pocket. Запросы должен исполнять тот же PocketApp и Harness. Терминал и iii используют ту же границу. BB не должен запускать своего агента для этой сессии.

Адаптеру нужны следующие возможности.

- постоянное соответствие BB thread, BB session и Pocket conversation, а также отдельная привязка subagent IDs;
- соответствие BB actor конкретному Pocket user. Один общий owner token не сохраняет различие полномочий;
- устойчивое соответствие исходного operation ID допустимому requestId;
- перевод событий `view`, live-данных, истории, tool calls, usage и изображений в формат клиента;
- восстановление состояния после отключения без повторного исполнения запроса с новым ID;
- перевод cancel, steer, интерактивных запросов ask и подтверждений. Без интерактивных ответов задача без web-клиента может ждать бесконечно;
- явный контракт совместимости и проверка истории, а не только отображение текущего текста.

Готовой серверной привязки BB с compare-and-swap, CAS, и нашим grant-контрактом в upstream не найдено. Обычный `POST /api/sessions` не имеет requestId в DTO. Поэтому потеря подтверждения создания сессии требует отдельного решения. Повтор этого POST не решает проблему.

Модель прав Pocket проще нашей. Она содержит роли owner, guest, viewer и список доступных корневых сессий. Выбор driver регулирует запись. Однако steering позволяет запускать команды с правами операционной системы сервера. Это не эквивалент нашим scoped grants и контролю внешних эффектов.

В локальном checkout `src/server/http/bb-origins.ts` читает `PI_POCKET_BB_ORIGIN` и строит CSP frame-ancestors. Эта настройка разрешает встраивание web в iframe, но не реализует BB adapter. Настройка не переносит историю, не связывает requestId и не передаёт полномочия BB. Обычный серверный HTTP-адаптер вообще не требует iframe-настроек.

Источники: [создание сессии](https://github.com/TannerMidd/pi-pocket/blob/50194aa38eb368ef2cb8599d44fba81b05ed5263/src/server/commands.ts#L407-L451), [доступ и driver](https://github.com/TannerMidd/pi-pocket/blob/50194aa38eb368ef2cb8599d44fba81b05ed5263/src/server/app.ts#L1949-L1990), [отправка и повтор запроса](https://github.com/TannerMidd/pi-pocket/blob/50194aa38eb368ef2cb8599d44fba81b05ed5263/src/server/commands.ts#L833-L914).

## Существенные проблемы

1. **Наш контракт требует усилить идемпотентность.** `clientKey` удаляет символы и обрезает ID до 64 знаков. Пустой результат получает новый UUID, поэтому повтор недопустимого ID может стать новым запросом. Commands не содержит явного fingerprint-конфликта по исходному DTO.

   Комментарий также описывает гонку. Два interrupt-submit могут оба остановить исполнение. Адаптеру нужны допустимые постоянные ключи и сохранение исходного намерения. Требуются отдельные проверки конфликта payload и потери подтверждения, lost-ACK. [requests.ts](https://github.com/TannerMidd/pi-pocket/blob/50194aa38eb368ef2cb8599d44fba81b05ed5263/src/server/requests.ts#L1-L20), [гонка interrupt-submit](https://github.com/TannerMidd/pi-pocket/blob/50194aa38eb368ef2cb8599d44fba81b05ed5263/src/server/commands.ts#L853-L883).

2. **Метаданные изображения не являются доверенными серверными данными.** Submit принимает `mime` и `size` клиента и использует их при проверке допустимости изображения. Upload ограничивает поток, но это не доказывает соблюдение 5 MiB на следующем этапе. Ошибка присоединения изображения может оставить сообщение без картинки. Для BB это риск незаметной потери входного содержания. Публичному адаптеру требуются серверная нормализация метаданных и явное подтверждение включения картинки. Источники приведены в [описании входных изображений](POCKET-REFERENCE.md#входные-изображения).

3. **Жалоба #265 сообщает о завершении сервера при GET /api/fs с EACCES.** Автор сообщает о воспроизведении на Android с Termux и 0.27.0. В исследовании этот случай не воспроизводился. Стабильный `http.ts` содержит `await` и `catch` с HTTP 500. Поэтому исходники не подтверждают заявленный механизм завершения процесса. Жалоба остаётся сигналом для проверки устойчивости, а не доказанным дефектом VPS. [Issue #265](https://github.com/TannerMidd/pi-pocket/issues/265), [обработка исключений HTTP](https://github.com/TannerMidd/pi-pocket/blob/50194aa38eb368ef2cb8599d44fba81b05ed5263/src/server/http.ts#L142-L163).

## Цена переноса и поддерживаемость

Без fork доступны отдельный сервер Pocket, необязательный UI, native drop-ins, внешние HTTP-клиенты и изображения. Pocket также предоставляет собственные функции памяти, подагентов и расписаний. Мы не обязаны поддерживать второй движок.

Наш терминал, BB и iii требуют собственного адаптера. Адаптер должен сопоставлять пользователей, преобразовывать историю и изображения, передавать отмену, интерактивные карточки и повторные запросы. Существующий dpi-sdk несовместим с сетевым API Pocket. Потребуется новая реализация его backend-границы либо новый клиент.

Изменения Pocket или расширение серверного API нужны для receipts, reconcile, надёжного создания сессии, grant-контракта и строгих image DTO. Также потребуется перенос native модулей с Host-specific зависимостями. Drop-in с собственными routes и documents может уменьшить fork. Однако такой drop-in не доказывает доступность всех внутренних операций через публичный host API.

**Перенос интерфейса не переносит историю и задачи.** Стандартный импорт Pocket работает с Pi JSONL и копирует активную ветку. Импорт не переносит наши Durable SQLite, состояние grants и bindings, а также выполняющиеся графы задач. Импорт не переносит собственный prompt, состояние расширений и изменения модели Pi. Незавершённый tool получает отметку `Not run`. [импорт Pi JSONL](https://github.com/TannerMidd/pi-pocket/blob/50194aa38eb368ef2cb8599d44fba81b05ed5263/src/server/pi-sessions.ts#L1-L17).

Совпадение версии Durable не делает базы приложений взаимозаменяемыми. У Host и Pocket разные документы, регистрации, каталог и политика. Нельзя автоматически переносить работающие задачи, разрешения, BB bindings, tool memos и credentials. Для истории нужен отдельно проверенный импорт с явным описанием потерь. Задачи необходимо завершить на старом владельце исполнения либо перенести специальной миграцией.

На уровне протоколов сохраняются провайдеры и совместимые модели. Также сохраняются файлы проектов и часть skills и prompts. Это не означает неизменность их загрузки и политик. Native Durable extensions переносимы только после проверки контрактов и lifecycle. Наши memory, tracing, Goal, MCP и guards нельзя считать сохранёнными из-за совпадения названий возможностей.

Стоимость первого прототипа без web-клиента умеренная, поскольку HTTP API уже существует. Цена совместимой замены Host существенно выше из-за протокола, политик, расширений и данных. Внешний адаптер проще сопровождать, чем широкий fork, но внутренний web API потребует закрепления версии и контрактных проверок. Чистое копирование отдельных Pocket-компонентов также создаст обязанность отслеживать их связи с PocketApp.

## Следующая проверка

До выбора Pocket остаётся проверить потерю подтверждения запроса, контракт BB, MCP и миграцию данных. [План изолированного эксперимента](POCKET-EXPERIMENT.md) сохраняет условия и порядок этих проверок.

Pocket предлагает готовый серверный продукт на том же Durable и уже решает передачу входных изображений. Он не снимает стоимость наших политик и адаптеров. До проверки lost-ACK, BB-контракта, MCP и миграции данных оснований заменять текущий Host целиком нет.
