# Отчёт о переключении и восстановлении Pi Durable Host

**Дата отчёта:** 31 октября 2026 года.  
**Предмет:** неудачная активация `c0019d7-unified-reload-20261030`, восстановление предыдущего Host и порядок завершения обновления.

> Документ сохраняет результаты предыдущего расследования. Состояния сервисов, PID и результаты проверок приведены на момент расследования, а не как непрерывно обновляемый статус. При сохранении этого отчёта повторное переключение и новые проверки рабочего Host не выполнялись.

## 1. Короткий ответ: где мы сейчас

**Мы не вернулись к старому автономному Pi. Мы остались на предыдущей версии нового Host.**

Нужно различать два перехода:

1. **От локального Pi к схеме «терминал → SDK → общий Host».** Эта схема уже работает.
2. **От предыдущего Host к последнему release с unified reload.** Именно это переключение сорвалось.

| Компонент | Фактическое состояние на момент расследования |
|---|---|
| Общий Host | Работает: `active/running`, PID `1438537` |
| Активный backend-release | `c0019d7-delm2` — предыдущий |
| Последний подготовленный release | `c0019d7-unified-reload-20261030` — **не активен** |
| Durable SDK | Уже **1.4.0** и в предыдущем, и в новом release |
| Терминал | Из отдельного release `terminal-model-skills-20261030-v1`, подключается к Host |
| Новые reload-возможности | Работающий Host их **не объявляет** |
| iii engine | Работает |
| iii worker | Не запущен; полный путь iii этим восстановлением не проверен |

**«Предыдущий release» здесь не означает «старый SDK».** Обновление касалось нашей интеграции и reload-механизма поверх уже установленного Durable 1.4.0.

## 2. Что пытались переключить

> 🧠 **From Hindsight memory (Shared Durable provider and extension reload integration)** — цель интеграции: общий Durable-владелец сессий и безопасная перезагрузка провайдеров/расширений без потери контекста, изоляции и сохранённых моделей.

Подготовленный `c0019d7-unified-reload-20261030` содержит новый пакет `@local/pi-durable-reload` и связанные изменения backend, SDK и terminal integration.

Но **подготовить и проверить пакет — не то же самое, что сделать его работающим backend**. Для первоначального подключения нового механизма требовалось переключить сервис на новый release и успешно восстановить существующие сессии.

Этого завершённого переключения нет. Проверенный `/v1/protocol` отвечал, но в его capabilities отсутствовали:

- `profile-reload.v1`;
- `runtime-refresh.v1`.

Это прямой признак того, что новые операции ещё не доступны через работающий Host.

## 3. Как именно произошёл сбой

Последовательность по сохранённому выводу переключения и диагностике:

1. **Дождались завершения активной работы.** Проверка перед переключением сообщила, что Host свободен; одно sleeping schedule сохранялось.
2. **Зафиксировали исходное состояние:** 33 сессии, 38 разговоров, 4399 записей истории, без недоступных сессий.
3. **Попытались запустить новый release.** Для сервиса оставался `TimeoutStartSec=30`.
4. **Новый Host не сообщил о готовности за 30 секунд.** Systemd завершил запуск по таймауту.
5. **Запустился автоматический откат на предыдущий release.** Путь запуска вернули на `c0019d7-delm2`.
6. **Предыдущий release тоже не запустился.** После прерванного запуска остались блокировки баз данных. Защита от второго владельца отказалась открывать их.
7. **Итог переключения записался как `rollback-failed`.** После этого терминалу было не к чему подключаться, и он показывал общий отказ запуска.

```text
Не хватило времени на запуск нового Host
                  ↓
Запуск прерван, остались блокировки
                  ↓
Автоматический откат тоже заблокирован
                  ↓
Host недоступен → терминал отказывает
```

### Почему восстановление требует больше 30 секунд

В `Store.open()` сохранённые сессии открываются последовательно. Только после их восстановления завершается подготовка Store и становится возможна готовность сервиса.

При ремонте **предыдущий release с теми же данными запустился за 85 секунд**. Это показывает, что лимит 30 секунд не соответствует наблюдаемому времени восстановления.

**Ограничение вывода:** это не доказывает, что новый release обязательно заработает при увеличенном таймауте. У него подтверждён таймаут запуска; возможные следующие ошибки ещё не проверены. Детальное распределение времени запуска не профилировалось.

## 4. Почему откат не спас автоматически

Здесь две разные стороны:

- **Защита данных сработала правильно:** сервис не стал молча игнорировать существующие блокировки и рисковать одновременным открытием баз.
- **Процедура переключения оказалась неполной:** она умела вернуть предыдущий путь запуска, но не смогла восстановиться после прерванной инициализации нового процесса.

В operational-service обработчики штатного завершения устанавливаются **после** `Store.open()`. Значит, прерывание во время открытия Store не проходит через тот же штатный обработчик закрытия, который действует после запуска.

То есть «вернуть прежний `ExecStart`» оказалось недостаточно для полноценного отката.

## 5. Почему 42 проверки и 2 smoke не означали успешный переход

Проверки и переключение отвечают на разные вопросы:

| Проверка | Что она подтверждает |
|---|---|
| Изолированные тесты | Поведение проверенных функций и сценариев |
| Проверки установленного пакета | Что проверялся собранный артефакт |
| Smoke | Что ограниченный сценарий запуска прошёл |
| Переключение рабочего Host | Что именно новый release восстановил рабочие данные и обслуживает клиентов |

В манифесте нового release записано `installedChecks: 42`. **Там же прямо указано, что манифест не является подтверждением активации**: результат активации нужно читать отдельно.

Отдельный результат переключения — `rollback-failed`.

Следовательно, прежние результаты тестов не закрывали фактически провалившийся сценарий: запуск под systemd с существующим набором сессий и рабочим таймаутом.

Предыдущая отметка **«100%» относилась только к аварийному восстановлению прежнего Host**, не к завершению обновления. Это следовало обозначить яснее.

## 6. Что уже исправлено

С разрешения пользователя выполнено восстановление, а не повторная активация нового release:

- Создана приватная резервная копия данных и конфигурации.
- Подтверждено отсутствие прежнего процесса и открытых им файлов данных.
- 13 блокировок умершего процесса перенесены в карантин, не удалены безвозвратно.
- Таймаут сервиса увеличен с 30 секунд до 5 минут.
- Запущен **предыдущий** `c0019d7-delm2`.

После восстановления проверены:

- сохранность IDs и моделей всех 33 сессий;
- наличие 38 разговоров;
- неизменность 4399 прежних записей истории;
- целостность SQLite;
- SDK discovery без недоступных сессий;
- подключение установленного терминала через `--continue`.

Sleeping schedule сохранилось, возобновилось и завершилось. Это ожидаемый эффект разрешённого восстановления, а не потеря задания.

Во время восстановления отдельно не проверялись создание новой сессии и отправка нового запроса модели.

## 7. Что ещё не исправлено и не переключено

**Последний backend-release не активирован.** Поэтому unified reload пока нельзя считать работающим в текущем Host.

Кроме того, остались вопросы к процедуре запуска:

- **Несогласованные таймауты.** Сервис теперь допускает запуск до 5 минут, но установленный terminal launcher ждёт `systemctl start` только 45 секунд. При холодном запуске терминал ещё может отказаться раньше готовности Host, хотя сам сервис продолжит запускаться.
- **Неполный аварийный откат.** Нужно проверить прерывание именно во время восстановления сессий и последующий безопасный возврат, а не только замену пути запуска.
- **Слишком общее сообщение терминала.** Оно объединяет недоступность Host, проблемы прав и ошибки аргументов. В этом инциденте видимая причина была на стороне запуска Host.
- **Полный iii-путь не подтверждён.** Engine работает, worker не запущен. Это отдельный незакрытый пункт, а не установленная причина отказа терминала.

## 8. Как правильно завершить переход

Рекомендованный порядок: **сначала подготовить надёжное переключение, потом повторить его один раз**.

1. **Согласовать время ожидания** сервиса, launcher и процедуры переключения. Терминал не должен объявлять отказ раньше допустимого срока готовности Host.
2. **Проверить кандидат на восстановлении сопоставимого числа сессий** в изолированной среде. Проверить не только успешный запуск, но и остановку посреди открытия Store, освобождение ресурсов и возврат на прежний release.
3. **Повторно проверить конечный установленный артефакт.** Не исходники вместо установленного release.
4. **В отдельное согласованное окно выполнить переключение:** дождаться безопасной остановки, сохранить свежую копию, запустить кандидат и дождаться готовности.
5. **Принимать обновление только по совокупности фактов:**
   - процесс действительно запущен из нового release;
   - Host доступен;
   - новые reload-capabilities объявлены;
   - сессии, модели и история сохранены;
   - терминал подключается;
   - reload проверен на выделенной idle-сессии;
   - затрагиваемые интеграции проверены отдельно.

До выполнения этих условий правильный статус: **«кандидат подготовлен; активация не завершена»**, а не «мы обновились».

Этот порядок — рекомендация, а не разрешение на новое переключение. Сохранение отчёта не запускает реализацию или активацию.

Файл неудачного переключения описывает **прошлую попытку**, а не текущую доступность Host. Его `pid: 0` не противоречит тому, что после ремонта Host работает.

Резервная копия содержит приватные данные. Её содержимое не следует переносить в репозиторий или прикладывать к публичному отчёту.

## Итог

Мы уже используем новую Host-архитектуру, но пока на предыдущем рабочем release. Сорвалась процедура обновления и затем её автоматический откат; доказательств, что сам новый reload-механизм принципиально неработоспособен, нет.

Восстановление завершено. Активация последнего release остаётся незавершённой. В рамках подготовки и сохранения этого отчёта рабочий Host не переключался.
